# plusplus

A healthcare and emergency-help app for **Karnataka, India**.

1. **Find care nearby** — hospitals, clinics and medical stores around you or in any area you choose.
2. **Find the right doctor and book** — pick your problem, get the best-matched doctors near you, and book at clinics and hospitals registered on plusplus.
3. **Emergency SOS** — when an accident happens, plusplus alerts nearby volunteer **3-wheeler (auto-rickshaw) and 4-wheeler drivers** who can take the injured person to the nearest hospital, because an ambulance can take a long time to arrive.

> plusplus **adds to** emergency services; it does not replace them. Every SOS also lets the user call **108** (ambulance) and **112** (national emergency number) with one tap.

Nobody near the border is wrongly blocked.

## Features

### 1. Find care nearby (works without login)
- Map view and list view, switchable.
- Categories: **Hospital**, **Clinic**, **Medical store / pharmacy**, plus filters for **Open now**, **24×7**, **Emergency / trauma care**, **Government / Private**.
- "Near me" (uses GPS) or "Choose area" (district / taluk / locality / PIN code).
- Each place shows: name, type, address, distance, phone (tap to call), opening hours, directions (opens Google Maps), and a **"Book appointment"** button if it is registered on plusplus.
- Search by name or speciality (e.g., "orthopaedic", "dental", "pediatric").

### 2. "What's your problem?" → best doctor for your condition
- User taps **"Find a doctor for my problem"** and picks what's wrong in one of three ways:
  1. **Common problems list** with icons (fever & cold, stomach pain, skin rash, tooth pain, back pain, joint/knee pain, eye problem, ear/nose/throat, pregnancy care, child is unwell, diabetes / BP check-up, anxiety / low mood, women's health, injury / sprain…).
  2. **Body-area picker**: tap head, chest, stomach, back, arms, legs, skin, then choose a symptom for that area.
  3. **Type it in** (v2, uses AI; see "AI models"): "my knee hurts when I climb stairs".
- **Describe it in your own words** (optional text box, v1): "Pain in right knee for 2 weeks, worse on stairs." This note is attached to the booking so the doctor reads it before the visit. Voice input (Kannada or English, via the phone's speech-to-text) is offered for people who prefer not to type.
- Follow-up questions (2–3 taps max): how long (today / few days / weeks), how bad (mild / moderate / severe), who is it for (adult / child / elderly / pregnant).
- **Choose the kind of doctor:**
  - **General doctor** (general physician / family doctor) — good first visit for most everyday problems; usually cheaper and available sooner.
  - **Specialist** — the app shows which specialist fits the problem (e.g. "Orthopaedic for knee pain"), and the user can change it from the specialities list.
  - **Not sure — suggest for me** (default) — the app recommends based on the answers: mild problems of a few days → general doctor first; long-lasting, severe or already-diagnosed problems (e.g. "diabetes follow-up") → specialist. It shows the reason in one line, and the user can switch with one tap.
- **Red-flag check comes first.** It checks both the picked options and the typed description (a keyword list in English and Kannada, e.g. "chest pain", "can't breathe", "unconscious", "bleeding a lot"). If the answers suggest an emergency (chest pain, breathlessness, fainting, stroke signs, heavy bleeding, severe injury, a child with high fever and drowsiness), skip doctor search and show **"This may be an emergency — Call 108 / Raise SOS / Go to nearest emergency hospital."**
- Otherwise the app maps the problem to one or more **specialities** (e.g. knee pain → orthopaedics, then general physician as a fallback; child unwell → paediatrics) using a doctor-reviewed mapping table.
- It then shows a **ranked list of doctors** at registered clinics (see "Doctor recommendation" under Algorithms), each with: speciality, qualifications, years of experience, languages spoken (Kannada / English / Hindi…), distance, consultation fee, rating, and the **next available slot**, with "Book" right there.
- Filters: General / Specialist (switchable at any time), specific speciality, distance, fee range, language, gender of doctor, available today, government / private.
- Clear note on screen: "This helps you choose a doctor. It is not a diagnosis."

### 3. Appointment booking (registered places only)
- Clinic onboarding: clinic signs up, uploads registration certificate (e.g., Karnataka Private Medical Establishments Act registration), platform admin verifies, then the clinic goes live.
- Clinic admin adds doctors (name, speciality, qualifications, consultation fee) and weekly time slots.
- User picks doctor → date → available slot → confirms. Booking is held atomically so two people can't take the same slot.
- Booking statuses: `pending → confirmed → completed`, or `cancelled` / `no_show`.
- Reminders: push notification 24 hours and 1 hour before the appointment.
- Cancel / reschedule up to a cut-off set by the clinic (default 2 hours before).
- **v1 has no online payment** — pay at the clinic. (Add UPI via Razorpay in v2.)

### 4. Emergency SOS (the core feature)

#### Who can raise an SOS
- The injured person, or a **bystander** reporting an accident they've witnessed.
- Requires a verified phone number (OTP) to stop fake alerts. Big red SOS button on the home screen.

#### SOS flow
1. User taps **SOS** → 5-second countdown with **Cancel** (stops accidental taps).
2. App captures GPS location, plus optional details: number of injured people, conscious/unconscious, a photo, a short note.
3. App immediately shows **Call 108** and **Call 112** buttons.
4. Backend finds **verified, available responders** near the location:
   - First search within **2 km**; if fewer than 3 responders are found, widen to **5 km**, then **8 km**.
   - Rank by distance, then by vehicle type (4-wheeler first if the patient may need to lie down; either is fine otherwise).
5. Responders get a **high-priority push notification** with an alarm sound, and an **SMS fallback** if the push isn't delivered within 15 seconds.
6. The **first responder to accept** is assigned. Everyone else is told "Help is on the way — thank you."
7. Alerts go out in **waves of 3**. If nobody in a wave accepts within **25 seconds**, the next wave is alerted and the radius widens when needed (see "Responder dispatch" below). Keep telling the user what's happening.
8. Once a responder is assigned:
   - The user sees the responder's name, vehicle type, vehicle number and **live location / ETA**.
   - The responder gets turn-by-turn directions to the scene, then to the **nearest hospital with emergency care** (suggested automatically from the directory).
   - The user and responder can call each other through a **masked number** (neither side sees the real phone number).
9. The hospital the patient is heading to gets an optional heads-up (if it's registered on plusplus).
10. The user's **emergency contacts** get an SMS with a live location link.
11. Statuses: `searching → assigned → en_route_to_scene → picked_up → reached_hospital → closed`, or `cancelled` / `no_responder`.
12. After the SOS: both sides can rate the experience and report problems.

#### Responder onboarding
- Sign up → upload **driving licence**, **vehicle RC**, vehicle photo, and a selfie → platform admin verifies.
- Vehicle type: `three_wheeler` or `four_wheeler`.
- Show a short in-app **basic first-aid and safe-transport guide** (how to move an injured person safely, when NOT to move them, e.g. a suspected spinal injury) that responders must read before going live.
- Responder sets themselves **Available / Unavailable**. While available, the app shares their location in the background (about every 30 seconds, more often during an active SOS).
- Responders can see their help history and thank-you badges.

#### Safety and abuse prevention
- Rate limit: maximum 3 SOS requests per user per hour.
- Fake alerts → warning, then suspension.
- Responders with repeated no-shows after accepting are paused.
- In-app explanation of India's **Good Samaritan protections** (Motor Vehicles Act, Section 134A) so people aren't afraid to help. *(Have a lawyer check the exact wording before launch.)*

### 5. Personal health features
- Emergency contacts (up to 5).
- Basic medical profile (blood group, allergies, ongoing conditions) — optional, and shared with the responder or hospital **only during an active SOS** and only if the user agrees.
- Saved / favourite places.
- Appointment history.

### 6. Languages
- **Kannada** and **English** from day one. All UI text goes through i18n files; nothing is hard-coded.

## Models, algorithms and GIS

### 1. AI models

**Inside the app (all optional; v1 needs no machine learning)**

| Feature | Approach | When |
|---|---|---|
| Problem picker (list + body-area) → speciality | **No AI needed.** A curated `problem → speciality` table reviewed by a doctor. Predictable, works offline, easy to audit. | v1 |
| Free-text "type your problem" → speciality (e.g. "knee pain when climbing stairs" → orthopaedic) | A small, fast LLM called from an Edge Function, returning only a speciality from a fixed list. **Never gives medical advice or a diagnosis.** If the text mentions red-flag words (chest pain, can't breathe, unconscious, heavy bleeding, stroke signs), skip the AI and show "Call 108 / raise SOS" immediately. | Phase 9+ |
| Automatic crash detection (phone detects a crash and offers SOS) | Start **rule-based**: accelerometer spike above ~4 g AND GPS speed drops from above 25 km/h to about 0 within 3 seconds → show "Are you OK?" with a 30-second countdown before raising SOS. Later, train a small on-device model (TensorFlow Lite) on real sensor data to reduce false alarms. | v2 |
| Better ETA prediction | Not needed; the routing API's traffic-aware ETA is good enough. | — |

### 2. Algorithms

#### a) Responder dispatch (the most important algorithm)

**Wave-based dispatch with a two-stage ranking.** Alerting everyone at once spams drivers; asking one at a time is too slow. Alerting in waves is the balance.

```
on SOS created at point P:
  radius = 2 km
  loop:
    # Stage 1: fast candidate search (PostGIS KNN, straight-line distance)
    candidates = 20 nearest responders to P within radius where
                 verified AND available AND last_seen < 2 min ago
                 AND not already alerted for this SOS

    # Stage 2: re-rank by real road time (one Route Matrix call: N origins → P)
    for each c: c.eta = road ETA from c to P (traffic-aware, mode = driving)
    score(c) = c.eta_seconds
             + 60  if location is 60–120 s stale
             + 120 if acceptance rate < 30% (min 5 past alerts)
             - 30  if vehicle is four_wheeler and patient is unconscious / can't sit
    wave = 3 lowest-score candidates

    send push (+ SMS after 15 s if not delivered) to wave
    wait up to 25 s for an accept
    if accepted → done (first-accept-wins, atomic UPDATE)
    if no one left in radius → radius = next of [5 km, 8 km]; if past 8 km → status no_responder, keep showing 108/112
```

- First-accept-wins: `UPDATE sos_requests SET assigned_responder = $1, status = 'assigned' WHERE id = $2 AND assigned_responder IS NULL RETURNING id`. Zero rows = someone else got it.
- Timers run in an Edge Function triggered by a scheduled job or a Postgres queue (`pgmq`), not in the phone app.
- Make all numbers (radius steps, wave size, timeouts, penalties) config values, and unit-test the ranking function as a pure function.

#### b) Choosing the destination hospital

Nearest isn't always right: a small clinic can't treat a road accident. In this order:
1. Filter: `has_emergency = true` AND (`is_24x7 = true` OR open now).
2. Take the 10 nearest by straight-line distance (PostGIS KNN) from the pickup point.
3. Re-rank by road ETA (one Route Matrix call).
4. Show the top 3 to the responder, best first, with ETA and a call button. Prefer hospitals tagged `trauma_care` when ETA difference is under 5 minutes.

#### c) Nearby search

- `ORDER BY location <-> :point` (PostGIS KNN using the GiST index) — fast "nearest N" without scanning the table.
- Filter with `ST_DWithin(location, :point, :radius)`; default radius 5 km in cities and 20 km in rural areas (use the taluk's urban/rural flag).
- Name search: `pg_trgm` trigram similarity, so typos like "manipal hospitl" still match. Store `name_en` and `name_kn` and search both.

#### d) Doctor recommendation ("best doctor for my problem")

**Step 1: problem → specialities (rules, not AI).**
`problem_specialities` table gives each problem a primary speciality (weight 1.0) and fallbacks (e.g. 0.6 for general physician). Answers to the follow-up questions adjust this: "child" → paediatrics added at 1.0; "pregnant" → obstetrics added at 1.0; "severe" → hospitals preferred over small clinics. Red-flag answers stop here and show the emergency screen.

Then apply the user's **doctor-type choice**:

| Choice | Speciality list used |
|---|---|
| General doctor | `gp` and `family_medicine` at 1.0 (for a child: `paeds` also at 1.0, since paediatricians are the usual first doctor for children in India) |
| Specialist | Only the problem's specialist specialities at 1.0; the GP fallback is removed. If the user picked a speciality by hand, only that one. |
| Not sure (default) | Run `suggestDoctorType()`: **specialist** if duration = weeks OR severity = severe OR the problem is flagged `usually_specialist` (e.g. eye, dental, pregnancy, skin, follow-up of a known condition); otherwise **general doctor**. Then use that row above, and keep the other type as a lower-weight fallback (0.5) so results are never empty. |

`suggestDoctorType()` is a pure function with unit tests, and returns both the choice and a short reason string for the UI.

If the user typed a description, it is **saved with the booking for the doctor**. In v1 it does not change the ranking; in v2 the AI step can read it to suggest the speciality, and its suggestion is shown to the user to confirm, never applied silently.

**Step 2: candidate doctors.** Verified doctors at registered places within the search radius (default 10 km city / 30 km rural) whose speciality is in the list, with at least one open slot in the next 7 days.

**Step 3: score and rank (weighted sum, each part normalised to 0–1):**

```
score = 0.30 × speciality_match      # weight from step 1 (1.0 primary, 0.6 fallback)
      + 0.20 × availability          # 1.0 if a slot today, falling to 0 at 7 days
      + 0.20 × proximity             # 1 − (road or straight-line distance / radius)
      + 0.15 × rating                # Bayesian average (see below), scaled to 0–1
      + 0.10 × experience            # min(years_experience, 20) / 20
      + 0.05 × language_match        # 1 if doctor speaks the user's app language
```

- **Bayesian rating** so a doctor with one 5-star review doesn't beat one with 200 reviews at 4.6:
  `rating = (C × m + Σ stars) / (C + n)`, with m = average rating across all doctors, C = 10, n = this doctor's review count.
- **Only patients with a completed plusplus appointment can review** that doctor, which stops fake reviews.
- Apply user filters (fee, gender, language, government/private) **before** scoring.
- Show the top 20; label the top 3 "Best match". Below each, show *why* ("Orthopaedic · slot today · 2.1 km · speaks Kannada") so ranking is transparent.
- Weights live in config and are tested as a pure function (`src/dispatch/rankDoctors.ts`). Never let paid promotion change the score; if sponsored listings are ever added, label them separately.

#### e) Merging places from several data sources

Google, OSM and HFR will list the same hospital differently. Treat two records as the same place when:
`ST_Distance < 75 m` AND `similarity(normalized_name_a, normalized_name_b) > 0.6`.
Keep one master row, store source IDs in a `place_sources` table, and prefer HFR > plusplus-verified > Google > OSM for each field.

#### f) Appointment slot locking

- `appointments.slot_id` is `UNIQUE`, so two bookings for one slot can't both succeed.
- Booking flow: mark the slot `held` with `held_until = now() + 5 min` using `SELECT … FOR UPDATE SKIP LOCKED`, confirm, then mark it `booked`. A scheduled job releases expired holds.

#### g) Responder location updates

- While available: send location every 30 s, or when the phone moves more than 100 m. During an active SOS: every 5 s.
- Drop GPS fixes with accuracy worse than 100 m; smooth with a simple moving average of the last 3 fixes to stop the marker jumping around.
- Saves battery and data, which matters on low-end phones.

#### h) Coverage analytics (admin, later)

- Bucket SOS requests and responder locations into **H3 hexagons** (resolution 8, roughly 0.7 km² each) using `h3-js` in an Edge Function or the admin panel.
- Heatmap of "SOS hotspots with no responder within 5 km" shows where to recruit more drivers.

```sql

-- People
profiles (
  id uuid primary key references auth.users,

  blood_group text, allergies text, conditions text,

emergency_contacts (id, user_id, name, phone, relation)

-- Places (hospitals, clinics, medical stores)

  ownership text check (ownership in ('government','private')),
  location geography(Point, 4326),
  address text, district text, taluk text, pincode text,

  specialities text[],

  verified_at timestamptz,
  source text                         -- 'google', 'osm', 'plusplus'
)
create index on places using gist (location);
create extension if not exists pg_trgm;
create index on places using gin (normalized_name gin_trgm_ops);
place_sources (place_id, source text, source_id text, fetched_at)   -- dedup across Google / OSM / HFR

-- Booking
doctors (
  id, place_id, name, gender, specialities text[], qualifications,
  years_experience int, languages text[], fee int,
  nmc_registration_no text,            -- medical council registration, checked during verification
  rating_sum int default 0, rating_count int default 0, verified_at timestamptz
)
specialities (code primary key, name_en, name_kn)          -- e.g. 'ortho', 'paeds', 'gp'
problems (id, code, name_en, name_kn, body_area, icon, is_red_flag bool, usually_specialist bool default false)
problem_specialities (problem_id, speciality_code, weight numeric)   -- doctor-reviewed mapping
reviews (id, appointment_id unique, doctor_id, user_id, stars int check (stars between 1 and 5), comment, created_at)
slots (id, doctor_id, starts_at, ends_at, status check (status in ('open','held','booked')), held_until timestamptz)
appointments (
  id, slot_id unique, user_id, status,
  problem_id, problem_description text,      -- user's own words, shown to the doctor
  doctor_type_choice text check (doctor_type_choice in ('general','specialist','not_sure')),
  duration text, severity text, patient_group text,   -- follow-up answers
  created_at
)
clinic_admins (user_id, place_id)

-- Responders
responders (
  user_id uuid primary key,
  vehicle_type text check (vehicle_type in ('three_wheeler','four_wheeler')),
  vehicle_number text, licence_doc_url text, rc_doc_url text,
  verification_status text check (verification_status in ('pending','verified','rejected','suspended')),
  is_available bool default false,
  last_location geography(Point, 4326), last_seen_at timestamptz,
  alerts_received int default 0, alerts_accepted int default 0   -- for acceptance-rate penalty
)
create index on responders using gist (last_location);

-- SOS
sos_requests (
  id uuid primary key, raised_by uuid, location geography(Point, 4326),
  injured_count int, is_conscious bool, note text, photo_url text,
  status text, assigned_responder uuid, destination_place_id uuid,
  search_radius_m int default 2000,
  created_at timestamptz, closed_at timestamptz
)
sos_alerts (id, sos_id, responder_id, sent_at, channel, response, responded_at)
sos_events (id, sos_id, status, location, created_at)   -- audit trail / timeline

-- Reference
karnataka_boundary (id, geom geography(MultiPolygon, 4326), source)
districts (id, name_en, name_kn, former_names, lgd_code, geom)
taluks (id, district_id, name_en, name_kn, former_names, census2011_code, lgd_code, is_urban, geom)
-- functions: is_in_karnataka(lat, lng), locate_in_karnataka(lat, lng) → district + taluk
```

### Key queries
- **Nearby places:** `ST_DWithin(location, :point, :radius)` ordered by `ST_Distance`.
- **Nearby responders:** `verification_status = 'verified' AND is_available AND last_seen_at > now() - interval '2 minutes' AND ST_DWithin(last_location, :sos_point, :radius)`.
- **Inside Karnataka:** `ST_Intersects(:point, (select geom from karnataka_boundary))`.
- **Accepting an SOS:** a single `UPDATE sos_requests SET assigned_responder = :id, status = 'assigned' WHERE id = :sos AND assigned_responder IS NULL` — only the first one succeeds.

### Security
- **Row Level Security on every table.** Users only see their own appointments, SOS requests and medical profile.
- A responder can see an SOS's details only if they received an alert for it, and its full details (medical info, exact location trail) only after they're assigned.
- Responder location is **never** shown to the public; only to the user they're helping, during an active SOS.
- Licence and RC uploads go to a **private** storage bucket; only admins can read them.

---

## Privacy and compliance

- Follow India's **Digital Personal Data Protection Act, 2023**: clear consent screens, collect only what's needed, let users download and delete their data.
- Medical profile and SOS data are sensitive. Encrypt them, keep access logs, and delete SOS location trails after 90 days (keep anonymised statistics only).
- Background location for responders needs clear permission prompts and a visible "You are available" notification while it's on.
- Never log phone numbers, medical info or exact locations in plain text.

## Operations

  `insert into public.platform_admins (user_id) select id from auth.users where phone = '91XXXXXXXXXX';`
- **SOS timer:** the SOS migration schedules `sos_tick()` every 5 s with pg_cron. Check with `select * from cron.job;`.
- **Notification sender:** deploy `supabase functions deploy send-notifications`, set its secrets (see the file header), then call it every ~10 s, e.g. with pg_cron + pg_net:
  `select cron.schedule('plusplus-send', '10 seconds', $$ select net.http_post('https://<project>.functions.supabase.co/send-notifications', '{}'::jsonb, headers := jsonb_build_object('Authorization', 'Bearer <service role key>')) $$);`
- **Places data:** `pnpm import:osm`, then load `supabase/.temp/osm_places.sql` with psql (service role).

## Conventions

- TypeScript strict everywhere; no `any`.
- Business rules (radius expansion, ranking, slot rules) live in pure functions with unit tests.
- All database access goes through Supabase with RLS; the service-role key is used only inside Edge Functions.
- Every user-facing string goes in `en.json` and `kn.json`.
- The SOS screens must work with large text, high contrast, and one hand. Keep them simple and fast.
- Use conventional commits (`feat:`, `fix:`, `test:`, `chore:`).
- When a behaviour is unclear, write a failing test that describes it first, then implement.
- **Never** remove or hide the 108/112 call buttons from any SOS screen.
